## 0.4.0: multi-model candidate status

The user requested a way to **actually add** related SO diffusers instead of merely viewing them in Xiaomi Cloud. Source 0.4.0 now allows the exact model IDs S6 (`bwj.diffuser.s6`), S2 (`bwj.diffuser.h10`), S7 (`bwj.diffuser.bw11`), S8 (`bwj.diffuser.s8`), S9 (`bwj.diffuser.s9`), S1 Pro (`bwj.diffuser.s1pro`), S1 (`bwj.diffuser.k09`) and S19 (`bwj.diffuser.s19`) to be **selected as experimental candidates**. The catalog distinguishes S5's field-confirmed GATT from published schema-only candidates. Each relative must be selected in Xiaomi Cloud, explicitly approved in the extra wizard step and authenticated over the chosen Bluetooth address before saving a credential. Normal S5 entry IDs and the legacy single-token path remain unchanged.

For published capabilities, S2/S6/S7/S8/S9 use the same high-level MIoT fields as S5. S1 Pro adds a diagnostic temperature property `3.10`; S1/S19 omit RGB properties. Source now filters light entities and exposes a read-only S1 Pro temperature sensor if a signed int8 notification is received. The vendor `LongSpray` switch stays **S5-only** because only its semantics have been tested. The code still uses an S5-derived GATT transport; relatives may fail the handshake, or authenticate but behave differently. **No non-S5 physical hardware acceptance has occurred; the operator has not yet run 0.4.0.**

This is deliberately different from Xiaomi Miot's broad cloud inventory: the official Xiaomi Home integration excludes Bluetooth products from supported controls, while Xiaomi Miot may discover their metadata without an applicable local GATT sender. See [multi-model architecture, analogous integrations and gate checklist](MULTI_MODEL_ARCHITECTURE.md).

## Discovery: S5-specific, not a universal Xiaomi rule

The `FE95` Xiaomi BLE service is shared by many devices. The integration recognizes exactly enumerated SO/BWJ model identifiers; an arbitrary Xiaomi FE95 advertisement or similar product name is never sufficient to classify an unknown device as compatible. S5 still has the original two known advertisement names, while the exact strings advertised by physical relatives require validation.

The picker and manual MAC fallback are implemented in the current source. Identification of the real S5 advertised name/product ID on more hardware and an evidence-backed compatibility matrix are outstanding.

## Token: exactly what is used and how to confirm it

- On new setup or **Reconfigure**, the integration initiates Xiaomi OAuth2 authorization and enumerates only exact allowlisted SO-family models. **S5** uses the previously field-reported flow. **Other models** require an explicit experimental confirmation and a real physical BLE Standard Auth handshake before token storage; passing handshake alone does not prove compatible property writes. Manual callback-URL fallback remains supported.
- Old entries without a provisioned per-device credential use `/config/so_s5_token` as a fallback. Loading an existing credential does **not** prove that a new cloud lookup was performed.
- Secrets are kept out of config entries; new entries retain only the BLE address, exact MIoT model and experimental opt-in flag. Existing entries without a model remain S5. The private token file is `/config/.storage/so_s5_ble_tokens.json` with mode 0600; OAuth access/refresh credentials are never persisted.
- For every BLE session, `coordinator.py` loads the token, establishes a GATT connection without pairing, constructs `S5ControlClient` and **awaits `session.authenticate()`** before setting `coordinator.connected = True`.
- `client.py` uses the **12-byte device GATT token** in the Xiaomi Standard Auth proof and derives the encrypted AES-CCM session. Without successful authentication, the runtime does not expose an available session for property commands.
- `S5Entity.available` mirrors `coordinator.connected`. Therefore, an S5 entity becoming **available** is evidence that this code path completed authentication; mere discovery or a configured integration is not.
- A successful power, spray, pause or light write provides stronger evidence: the client waits for an accepted `SetPropertyResp` and an exact matching `PropertyChanged` value. Intermediate stale notifications are ignored during the bounded wait; a true rejection or missing final confirmation still raises an error. Separately observe the physical response where applicable.
- The credential is the 24-hex-character S5 `token` returned by the Xiaomi device list during new OAuth onboarding, or imported through the legacy standalone extractor. It is **not** `BLE_DATA.beaconkey`. Never display, paste into an issue, log, or commit either secret.

**HA UI-only check:** Settings → Devices & services → Xiaomi SO Diffuser BLE → device → entities. Verify that entities are available rather than `Unavailable`, confirm plausible live sensor/state updates, then toggle the Diffuser power switch and independently check the actual device. If the device is only discovered but entities remain unavailable, the valid-token/connection milestone is not yet established.

**Credential safety for installations that still use the old token:** the runtime prefers a per-device token from `.storage`, then falls back to `/config/so_s5_token`. Do not delete an *existing, working* legacy token before completing verified migration. **For the operator's checked HA instance specifically, this file was already intentionally removed**, as was the new store and the component folder, and the persisted `so_s5` entry count is zero. Its next step is **fresh Add integration**, not Reconfigure. See [deployment audit](DEPLOYMENT_AUDIT_2026-11-07.md).

**Current limitation:** there is no explicit, user-facing `Token authenticated` diagnostic entity or positive authentication log. Add a **non-sensitive** connection/authentication diagnostic in a later release; it must never expose the token, derived keys, login frames or cloud credentials.

**Cloud boundary:** new-source OAuth provisioning is implemented as an on-demand setup/reconfigure feature; the external extractor is a fallback. **The operator confirmed browser OAuth setup and a functioning S5 on 2026-11-07**; the callback hostname needed a manual browser destination substitution to the accessible HA LAN address. Routine property operations still run over local BLE, while post-restart WAN-off control, token lifetime/rotation and other models remain unverified. Per-device credentials are stored separately.

## Continuous spraying: user-tested mode and UI

The original Mi Home UI calls this `LongSpray` and uses **property `3.4 = 0`**, whereas ordinary between-spray pauses use **3–30 minutes**. On 2026-11-07 the user **physically confirmed continuous spraying** on their connected S5. This is a direct user-reported hardware observation, not an independent device/firmware matrix or a long-duration endurance test.

- The HA switch is now **Continuous spraying**, writing `3.4 = 0` when turned on.
- Turning it off writes the last remembered ordinary pause, or **3 minutes** when no previous value is known.
- The separate spray pause slider shows no ordinary pause value when `3.4 = 0`.
- The remembered pause is runtime-only and may reset to 3 minutes after an HA restart.
- The power switch has been renamed **Power** (a stateful HA on/off switch, not a button); its unique ID remains unchanged. Continuous spraying still selects `3.4=0`, but must not be interpreted as a guarantee of mechanically nonstop vapor output. User-customized HA labels may remain unchanged.

**Decision:** keep continuous spraying as a normal supported, explicitly named control for this device. Revalidate switching **off** and pause restoration, including after reconnect/restart; measure other firmware revisions before generalizing compatibility.

## Regression: false read-back mismatch after a successful action

**User report:** a `switch/turn_off` action physically succeeded, but HA reported `S5 property read-back did not match the request`.

**Cause identified in code:** `PropertyChanged` notifications are not correlated by command transaction ID. The prior implementation immediately failed a pending command upon the first different value; a queued notification with the **old** state could arrive before the requested final state.

**Fix:** when the property type matches but the value is different, continue waiting for the **exact requested state** within the existing timeout. The client still requires the successful matching `SetPropertyResp`, fails a true rejection or invalid type, and times out if a correct value never arrives. This does **not** treat a physical action alone as a protocol success. Synthetic regression cases cover stale `3.4 = 0` before a restored pause, and stale power ON before OFF. Live re-test of the updated code remains pending.

**User acceptance steps:** toggle both Power and Continuous spraying on/off, verify physical effects, confirm there is no spurious HA error, and check that genuinely unacknowledged commands still fail. Never publish raw token or encrypted captures.


## Verified offline evidence (2026-11-06 baseline)

- Both HMAC login proofs in the private supplied capture validated against the S5 device token.
- 272/272 AES-CCM frames authenticated: 3 transmitted, 269 received.
- 266 PropertyChanged and 3 matching successful SetPropertyResp messages decoded; 2,394 property values parsed.
- Initial 0.3.0 baseline: 57 pytest tests + 48 subtests passed. **After the 2026-11-07 regression fixes: 63 tests + 48 subtests passed on GitHub Actions.**
- The extractor's `BLE_DATA.beaconkey` is not interchangeable with the device GATT token.

These results do not validate the current user's live device or prove the physical effect of spray/light commands.


## Live field milestone and follow-up (2026-11-07)

The operator installed the updated custom integration, chose the detected SO S5, opened the Xiaomi browser authorization link and successfully completed the return callback by changing the *browser's destination hostname* from `homeassistant.local` to the reachable HA LAN IP, **without changing the OAuth code, state or callback path**. The operator reports that setup and the diffuser then worked. Since the previous local token and per-device token store were both absent on the checked installation, this is practical evidence for fresh acquisition through Xiaomi Cloud. The repository code only persists the device-specific 12-byte GATT token after the S5 BLE authentication challenge succeeds; HA's runtime reads that per-address token, not the OAuth access token. The new file has not yet been independently inspected after restart.

For S2/S7/S8/S9, the published MIoT property maps are very similar to S5; S19/S1 lack the light/colour fields. This **does not** justify enabling their BLE discovery or token exchange automatically. See [compatibility matrix and protocol acceptance](SPRAY_MODES_AND_COMPATIBILITY.md).

**Scheduling decision:** prefer native HA automations. Keep undocumented S5 timer-mask writes (`3.5`, `3.7`) disabled until a device-side scheduler is proven and intentionally opt-in. Existing Mi Home schedules may still affect device behaviour and should be checked when investigating irregular spraying.
